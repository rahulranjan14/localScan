localScan Runtime Map

Six packages, two of your own ports, one durable pipeline, and a hash that two processes resolve to different directories.

Drawn from the code and from the processes actually running on this machine — ports measured with lsof, flow read from workflows.ts, role states read from /api/system. Written 12 October 2026 against 495834a; the directory-split section is kept as a record of a defect since fixed (D-015).

TopologyWhat talks to what

Everything except the models runs on the laptop. The browser never reaches Postgres or Temporal; the server never calls a model. Model calls happen only inside worker activities, which is what makes them resumable.

The one surface shared by humans and agents is port 3000: the REST API and the MCP endpoint are the same socket on the same process.

ExecutionOne upload, end to end

The upload returns a run id, not a result. The server hashes the bytes, writes them to disk, checks whether that hash is already stored, and starts a workflow named extract-<first 16 of sha256> — content-addressed, so the same PDF cannot race itself. Then it hands the connection back.

The workflow itself is deliberately boring: a fixed sequence with one branch and no model-chosen control flow. What earns Temporal its place is the policy on each step, because the steps differ by two orders of magnitude.

Fixed · D-015Where the hash became a path

This has been fixed — the figure below records what was wrong, because the shape of the mistake is the useful part. Only the hash crossed the process boundary: the server wrote the bytes and discarded the absolute path it had just computed, and the worker rebuilt a path from the same hash. Both resolved the string data against their own working directory, and under npm run dev those directories differ.

dataDir() is now anchored to the workspace root, found by walking up from the module's own location, and storedFilePath() is the single definition of where a document's bytes live. Rows written before the fix are resolved against the repository root, which is what they meant, so documents stored then open without rewriting data.

Why a two-day-old commit surfaced only now

Before c7acd21 (9 Oct, “start the worker with the app”), npm run dev started the server and the interface but not the worker — you ran the worker yourself, from the repository root. That commit moved it under concurrently, which runs each workspace script in its own directory. The first upload through the full three-process dev stack was the first time the two sides disagreed, and the files table shows it: every row written before 11 Oct resolves to the repository root.

RetrievalAsking a document a question

Extraction and question answering are different problems, and they get different machinery. Extraction is a fixed sequence that must survive a crash, so it is a Temporal workflow. Answering is a loop whose next step depends on a model's judgement, so it is a LangGraph graph — in-process, no durability, because a failed answer costs one retry by the user.

AgentsThe same engine without a browser

Six MCP tools on port 3000, over the identical services the REST API uses. An agent can extract, browse, ask and check status; nothing in the MCP path reimplements the pipeline.

  • list_document_typesWhat this engine can extract into typed data.
  • extract_documentSubmit a document and get the run.
  • get_documentOne document by id, with data and form layout.
  • list_documentsBrowse, filtered by type or status.
  • ask_documentThe graph above, with page citations.
  • get_engine_statusWhich model serves which role, and whether it answers.
